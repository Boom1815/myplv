01

Dépôt de code — constat & résolution

Avant l'audit du site, un constat factuel sur l'environnement dans lequel cette session s'est exécutée.

Constat initial

Le dépôt GitHub connecté par défaut à cette session (Boom1815/Tof-Box) contenait déjà une application complète, en production, sans aucun rapport avec MYPLV : « Tof-Box », une app grand public avec parrainage, coffre-fort numérique, partage d'objets, TofMeet, facturation Stripe, et des builds iOS/Android via Capacitor.

Construire la plateforme MYPLV à l'intérieur de ce dépôt aurait mélangé deux produits sans lien, avec un vrai risque d'écraser du code de production existant — contraire au principe n°13 du brief (« ne pas supprimer l'existant sans plan de migration »). La question a été posée avant d'agir : un nouveau dépôt dédié a été retenu.

Résolu

Le dépôt Boom1815/myplv a été créé, ce rapport y a été poussé sur main. Tof-Box n'a été touché à aucun moment. Tout le développement à venir se fait dans ce nouveau dépôt.

02

Résumé exécutif

Ce que je recommande, en une minute de lecture.

  • Ne pas toucher au site Wix existant dans un premier temps. Le reconstruire n'apporte aucun bénéfice technique pour le projet de prospection, coûte du temps de conception/contenu, et fait courir un risque SEO évitable. À réévaluer plus tard, séparément.
  • Construire la plateforme de prospection comme application séparée, sur app.myplv.be — nom confirmé — pointé par un enregistrement DNS CNAME géré depuis le registrar tiers vers le nouvel hébergeur, sans quitter Wix pour le site public.
  • Sources de prospects : Open Data KBO/BCE (fichier complet + mises à jour mensuelles, gratuit, avec inscription) comme socle, complété par l'API publique gratuite CBE API pour les recherches ponctuelles.
  • Email : Brevo, plan gratuit — 300 emails/jour (6× la cible de 50/j), SPF/DKIM/DMARC inclus, API + SMTP, sans carte bancaire.
  • Stack et hébergement à 0 €/mois réalistes : Cloudflare Pages + Workers (frontend + API, usage commercial autorisé — à confirmer dans les CGU avant mise en production), base Postgres gérée par Neon, jobs planifiés via GitHub Actions.
  • Toutes les décisions ci-dessus sont validées (25/08) — voir section 16. Prêt à démarrer la Phase 1.

05

SEO — ce qui est connu

Sans accès direct au site, je ne peux pas produire le tableau complet ancienne-URL → nouvelle-URL demandé par le brief (section 12 du prompt maître) — il n'y a d'ailleurs pas de nouvelle URL à ce stade, puisque la recommandation (section 6) est de ne pas migrer le site public. Ce qui est établi par l'indexation Google :

  • Le site est indexé (plusieurs pages ressortent dans les résultats), signe qu'il n'y a pas de blocage robots.txt flagrant.
  • Les titres de page suivent un format cohérent : Nom de page | MyPLV I [accroche] — bon signal de discipline SEO existante.
  • Puisque l'architecture recommandée (section 7) laisse myplv.be inchangé, le risque SEO de ce projet est nul par construction : aucune URL publique ne change.

Pipeline quotidien (horaires configurables, déclenché par GitHub Actions qui appelle des endpoints protégés par un CRON_SECRET) :

import KBO→ normalisation→ dédoublonnage→ géo + NACE→ blacklist→ scoring→ segmentation→ mode validation→ envoi (≤50/j)

13

RGPD & sécurité

Contact RGPD — confirmé le 25/08

Pierre Bataille, joignable via info@myplv.be, est le point de contact désigné pour toute question RGPD (droit d'accès, opposition, réclamation) et pour la validation finale du cadre légal de prospection avant l'envoi de campagnes en volume. Cette adresse doit apparaître comme reply-to et être mentionnée dans la politique de confidentialité liée aux emails de campagne.

  • Base légale envisagée : intérêt légitime (art. 6.1.f RGPD) pour la prospection B2B vers des adresses génériques d'entreprise (info@, contact@) — cadre reconnu par la CNIL et l'APD belge, à condition d'informer dès le premier contact et d'offrir une désinscription immédiate.
  • Une adresse nominative (prenom.nom@) reste une donnée personnelle même en contexte professionnel : traçabilité et droit d'opposition doivent s'appliquer de la même façon.
  • Suppression list globale, contrôlée avant chaque envoi (section 56 du brief) ; conservation/anonymisation après un délai à définir avec toi (le brief suggère une pratique de marché à 3 ans d'inactivité, à valider juridiquement).
  • Secrets hors code (.env, jamais committé), permissions ADMIN/READER dès le départ, journal d'audit sur toute action destructive.
Rappel du brief, maintenu tel quel

Le logiciel ne garantit pas à lui seul la conformité RGPD. Les règles de prospection doivent être validées par un juriste avant tout envoi à grande échelle — je peux construire les garde-fous techniques, pas trancher la question juridique.

Risques & limites

  • Audit du site public incomplet : sans accès réseau direct à myplv.be depuis cet environnement, la confirmation Wix et l'inventaire SEO restent basés sur l'indexation, pas sur une inspection directe.
  • CBE API (tiers) n'est pas un service officiel du SPF Économie : dépendance à surveiller, ne pas en faire une source critique irremplaçable.
  • Réputation email sur IP mutualisée gratuite : à surveiller dès les premiers envois réels, avant tout passage en volume.
  • Paliers gratuits (Cloudflare, Neon, GitHub Actions) peuvent changer sans préavis — l'architecture doit rester interchangeable (déjà prévu via les abstractions DataSourceAdapter / EmailProvider).
  • Conformité RGPD : cadre technique prêt, validation juridique non incluse (rappel section 13).
